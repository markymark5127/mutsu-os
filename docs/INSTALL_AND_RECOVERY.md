# Mutsu OS — Install, Update, and Recovery

This document covers the current state of distribution, installation, updates, and recovery for Mutsu OS. It is **not** a claim that a public beta or signed release exists. See the [roadmap](ROADMAP.md) and open issues for remaining gates.

## Current image status

- OCI images are intended to be built and published to GHCR by the `.github/workflows/build.yml` workflow on trusted `main` pushes (after preflight checks).
- Signing uses Cosign when `SIGNING_SECRET` is configured. Verify repository settings before relying on signatures.
- Disk images / ISOs are generated by `build-disk.yml` **after a successful main-branch container build** or via manual dispatch. Both paths require a published commit-specific image, resolved to an immutable OCI digest before OSBuild. The Anaconda branding injection preserves the original ISO boot metadata via xorriso replay. The legacy `anaconda-iso` output has **not yet passed an installed-VM/physical boot test** (tracked in #11). See [Initial install QA](INITIAL_INSTALL_QA.md).
- No public download page or signed release artifacts are currently published.

### Supported disk blueprints

**Use only `disk_config/iso.toml` for the GNOME installer ISO and
`disk_config/disk.toml` for QCOW2.** Two unused experimental KDE/GNOME
blueprints were removed after review: they contained `bootc switch`
commands targeting the generic `ghcr.io/ublue-os/image-template:latest`
rather than Mutsu OS. They were not part of the shipping disk workflow.
Mutsu OS currently builds a **GNOME** image; there is no supported KDE
installer image.

The disk workflow checks the exact image SHA and produces build-info and
SHA256 checksum files. A valid build artifact still does not prove that a
UEFI VM completed Anaconda installation and first login. Do that test
before installing to physical hardware.

## Building and testing locally

```bash
git clone https://github.com/markymark5127/mutsu-os.git
cd mutsu-os
just build          # produces an OCI image (requires Podman)
```

For disk images, follow the Justfile recipes and `disk_config/` notes. Always test in a disposable VM.

## Installing

Until a verified installer is available:

1. Prefer a disposable QEMU/VirtualBox VM.
2. Use the generated qcow2 or ISO only after confirming the workflow produced a bootable artifact.
3. Do **not** rebase a daily-driver machine until M0 gates (especially #8, #11, #13) have attached evidence.

**Interactive installer (`generic-iso`):**
The Fedora 44 Anaconda ISO embeds an immutable Mutsu OS bootc image and
presents interactive disk, account, language, and network configuration.
There is no unattended wipe in Mutsu's installer configuration. Nevertheless,
formatting or reusing a partition in Anaconda **destroys data on the selected
partition**. Back up important data and test the image in a disposable VM
before using a real machine.

### Disk-backed scratch for the offline container

The live installer's writable root, including `/var/tmp`, is too small for
Mutsu's large embedded image. Without disk-backed scratch, `bootc install
to-filesystem` can fail with `/var/tmp/container_images_*: no space left on
device`, even when the installation partition has hundreds of gigabytes free.

The installer-only `/usr/bin/bootc` wrapper now checks that Anaconda has mounted
the selected target at `/mnt/sysimage`, checks for at least **48 GiB** free
space, creates a temporary folder under that target's `lost+found`, and
bind-mounts it over the live `/var/tmp` while bootc imports the image.
Using `lost+found` is intentional: bootc exempts it from the destination's
empty-root requirement. An exit trap removes the temporary mount and folder
on both success and failure. Other bootc operations use the unmodified
binary. This workaround does **not** select, repartition, or wipe disks.

This is a source-level fix with build-time checks; a successful full-size
installation and boot on real hardware still needs to be verified. Do not
wipe another drive or buy RAM to solve the installer overlay's ENOSPC error.

Mutsu OS is the product name. Upstream Bazzite / Universal Blue / Fedora credits and technical IDs are preserved so updates remain compatible.

## Updates and rollback

Mutsu OS is a bootc image. Standard bootc / rpm-ostree patterns apply:

- `bootc upgrade` (or the image's update mechanism) pulls a new deployment.
- `bootc rollback` reverts to the previous deployment.
- User state under `/var` and `/home` is preserved across atomic updates when using the normal bootc layout.

Document any Mutsu-specific overrides here once verified. Fallback to a pure Bazzite rebase remains possible if the Mutsu layer is removed, but test this path before relying on it.

## Early boot emergency shell (dracut)

If the installed VM shows `Generating /run/initramfs/rdsosreport.txt`
and drops to emergency mode, it failed **before** GNOME, Newelle,
or keyboard shortcut services started. From the dracut prompt collect:

```sh
cat /proc/cmdline
blkid
tail -n 100 /run/initramfs/rdsosreport.txt
```

Check that the VirtualBox disk controller and virtual drive are connected.
Compare the root UUID in the kernel command line to the output of `blkid`.
Do not wipe a VM or manually edit its Btrfs subvolumes until the reason is
known.

An earlier Mutsu Containerfile ran plain `dracut -f` from inside the
build container, risking a host-only initramfs which lacks a target
machine's storage modules. The alpha now preserves the original Bazzite
generic initramfs, with custom Mutsu Plymouth artwork staged for future
boot-tested integration. This is a **candidate fix**, not proof that
every dracut emergency mode is caused by the overwritten initramfs.

## Recovery

- If GNOME fails to start because of the Adaptive Desktop extension, disable it from a TTY or recovery shell:
  ```bash
  gnome-extensions disable mutsu-adaptive@mutsu-os
  ```
  Or use GNOME Extensions / Settings once a session is available. The extension is **not** enabled by default in the image.
- First-run wizard state lives in `~/.config/ai-desktop/onboarding.json`. Removing or editing it re-triggers the wizard for that user.
- Wallpaper and shortcut defaults are overridable; they do not lock user choices.
- No user API keys or Newelle credentials are baked into the image.

## Release process (planned)

1. Pin and document the exact `ai-desktop` commit and image digest.
2. Attach CI logs, boot screenshots, and rollback evidence to the relevant issues.
3. Require manual approval before publishing any public beta artifacts.
4. Publish SHA256 checksums and clear hardware compatibility notes with any download.
5. Keep upstream attribution in source and licensing; user-facing surfaces show Mutsu OS.

See issue #24 for the full acceptance checklist. This document will be updated when verified artifacts exist.
